# 0006 — Message ids and conversation order
> **Amended by 0014:** the `failed` state is withdrawn; messages without a `seq` are only `pending`.
- Status: proposed (awaiting G0)
- Date: 2026-10-13
- Author: TL (agent, claude-opus-5-5)
- Spec ids driven: `CORE-ENV-002`, `CORE-SEQ-*`, `CORE-SRV-030`..`CORE-SRV-033` — in [`spec/core/protocol.md`](../../spec/core/protocol.md) and [`spec/core/server-behavior.md`](../../spec/core/server-behavior.md)

## Context
The brief requires both clients to "behave identically" in the Alice/Bob scenario, where Alice and Bob each compose a message while offline (steps 3 and 4) and those messages reach the server later in a different order (Alice's at step 5, Bob's at step 7). Each client must merge its own sent messages, its queued messages and the messages it receives into one conversation, and both participants must end up with the **same** order.

## Decision
1. **Message id:** generated by the client at compose time, a lowercase UUID version 4 (36 chars). It is the identity of the message everywhere (dedupe, retries, extensions referring to messages).
2. **Order is assigned by the server.** On accepting a new envelope the server assigns `seq`: one counter for the whole server (per epoch), starting at 1, incremented by 1 per accepted envelope. The send response returns `seq` to the sender; the delivered envelope carries it to the recipient.
3. **Render order of a conversation** (both clients, identical):
   - every message with a `seq` (state `sent` or `received`) sorts by `seq` ascending;
   - every message without a `seq` (state `pending` or `failed`) sorts **after all sequenced messages**, by local enqueue order;
   - nothing else (client clocks, `created_at`, arrival time) affects order.
4. The **per-recipient cursor** (0004) is expressed in this same `seq`: a mailbox is the subsequence of envelopes with `to = owner`, so its `seq` values increase but have gaps.

Scenario consequence: A1 = 1, B1 = 2, A2 = 3 (accepted at step 5), B2 = 4 (accepted at step 7). Bob's final view is A1, B1, A2, B2; Alice's view after she reconnects again is the same.

## Alternatives considered
- **Per-recipient sequence (one counter per mailbox).** Gives contiguous cursors, but a message has a different number in each direction, so Bob cannot place his sent B1 (numbered in Alice's mailbox) against received A2 (numbered in his own). Two counters per message would be needed. Rejected in favor of one global counter.
- **Per-conversation counter.** Works for 1:1 but not for a future group or cross-conversation cursor, and needs a conversation id in core. Rejected; the global counter covers both.
- **Client timestamps (`created_at`).** Clock skew between emulator and browser; ties; offline messages composed earlier would jump above messages already seen. Rejected; `created_at` is informational only.
- **Lamport / vector clocks.** Deterministic but expensive to specify and still needs a tie-break; overkill for a relay that already sees every message in one process.
- **Server-assigned server timestamp.** Equivalent to `seq` but with ties at ms resolution. Rejected.

## Consequences
- Order reflects **when the server accepted** a message, not when it was typed. In the scenario Bob typed B2 before he saw A2, yet A2 renders first. The PM must state this in visible behavior.
- A pending message may move up when its ack arrives if a received message with a higher `seq` was rendered first (rare; final order is still deterministic).
- Global `seq` reveals total server traffic count; irrelevant for a local demo.
