# P2 server: spec questions raised by DEV

The server and its tests follow the spec text. Where the text is silent or two rules disagree, the server does the
smallest thing that keeps the contract valid, and the point is listed here for TL (spec edits are not DEV's). Each
entry says what the server does today, so a spec decision either confirms it or names the change. None blocks P2.

| # | Where | Question | What the server does now | Test |
|---|---|---|---|---|
| S-1 | CORE-ENV-005, CORE-SRV-030 step 2, CORE-ERR-002 vs section 12 table | A `payload` that is not a JSON object (string, array, number, `null`): is it `malformed_request` ("a field of the wrong JSON type", SRV-030 step 2, ERR-002) or `invalid_payload` (table: "or `payload` is not an object")? The two texts conflict. | `400 invalid_payload`, decided at step 4 (after epoch, names, id, type). | `test_CORE_ENV_005_payload_must_be_a_json_object` accepts either code and only requires 400. |
| S-2 | CORE-ENV-006 vs CORE-SRV-034, CORE-MSG-001 | ENV-006 says `created_at` MUST NOT influence dedupe, but SRV-034 and MSG-001 compare `created_at` and answer `409 id_conflict` when it differs ("all fields equal"). | SRV-034 / MSG-001 (more specific): a resend with another `created_at` is `409 id_conflict`. | `test_CORE_SRV_034_any_difference_is_409_id_conflict_and_changes_nothing`. |
| S-3 | CORE-POLL-001, CORE-POLL-004, `common.schema.json` `cursor` | `after` may have 16 digits (up to 9999999999999999) but the schema caps a cursor at 9007199254740991. With no envelope to return, `next_cursor` = `after` unchanged (POLL-004), so a legal request can get a response that fails `poll-response.schema.json`. | Echoes `after` as POLL-004 says. | `test_CORE_POLL_001_...` calls that case with schema validation off. Fix options: cap the `after` pattern at 15 digits, or reject `after` above 2^53-1 with `malformed_request`. |
| S-4 | CORE-HTTP-003, CORE-SRV-011 | Which `Content-Type` values count as `application/json`? "a `charset=utf-8` parameter is allowed" does not say what happens to other charsets or other parameters. | Media type compared case-insensitively; the only accepted parameter is `charset=utf-8` (quotes allowed); anything else, including `charset=latin-1`, is `415`. | `test_CORE_SRV_011_wrong_or_missing_content_type_is_415_on_both_posts`. |
| S-5 | CORE-HTTP-006, section 8 | A known query parameter given twice (`epoch=a&epoch=b`, `after`, `limit`): ignored, first wins, last wins, or bad parameter? | `400 malformed_request` ("bad query parameter"). Unknown parameters stay ignored, also when repeated. | No dedicated test (decision pending). |
| S-6 | Section 1 "Endpoints", CORE-NAME-003 | Path matching details: is a percent-encoded name segment decoded before validation (`%41lice`)? Is `/v1/mailboxes//messages` a known path with an empty name (`invalid_name`) or an unknown path (`not_found`)? Is `/v1/info/` unknown? | Segment is percent-decoded, then validated. Empty name: known path, `400 invalid_name`. A trailing slash makes the path unknown (`404`). | `test_CORE_NAME_001_CORE_NAME_003_path_name_is_validated_and_canonicalized`, `test_CORE_NAME_001_empty_path_name_is_invalid_name`, `test_CORE_ERR_001_CORE_HTTP_002_unknown_paths_...`. |
| S-7 | CORE-SRV-005 | `OPTIONS` "to any `/v1` path" is `204`: does that include paths that are otherwise unknown (`/v1/nothing`)? | Yes, literally: `204` for `/v1` and every path below it; `404` for `OPTIONS` outside `/v1`. | `test_CORE_SRV_005_options_is_204_with_preflight_headers_on_every_v1_path`. |
| S-8 | Section 1, section 12 | `HEAD`, other methods and the `Allow` header are not mentioned. | `HEAD` on a known path is `405 method_not_allowed` (E1 and E5 list `GET` only), headers and no body; no `Allow` header; an unknown method name is `405` on a known path and `404` otherwise. | `test_CORE_ERR_001_head_and_unusual_methods_get_the_matching_status`. |
| S-9 | CORE-ERR-001, section 12 | Requests that fail before routing (garbage request line, unsupported HTTP version, oversized request line or headers) need an error body with a code from the table, but no row names them. | `400 malformed_request` with the error body, connection closed. | `test_CORE_ERR_001_garbage_request_lines_still_get_a_json_error_body` (any 4xx with a body). |
| S-10 | CORE-HTTP-001, CORE-SRV-030 step 2, CORE-SRV-035 | Duplicate keys inside one JSON object, and nesting depth, are unspecified. | Duplicate keys: the last one wins (standard parser behavior). Nesting deeper than the interpreter's recursion limit (about 1000 levels) is rejected as `400 malformed_request`; the body limit alone would allow more. | `test_CORE_HTTP_001_CORE_SRV_030_body_must_be_one_utf8_json_object` (60000 nested arrays). |
| S-11 | CORE-SRV-002, CORE-SRV-006 | Is IPv6 (`--host ::1`) in scope, and is the host in the listening line the configured string or the resolved address? | IPv4 only; the line prints the configured host string and the actual port. | `test_CORE_SRV_006_...`. |
| S-12 | CORE-SRV-030, CORE-ERR-002 | Field-check order is listed for E3 only. For E2 the order is derived from ERR-002 alone (JSON, missing or unknown fields, wrong types, `capabilities` format, then `invalid_name`). | As derived. | `test_CORE_ERR_002_malformed_capabilities_win_over_invalid_name`. |
| S-13 | CORE-EPOCH-001, Appendix A | Appendix A fixes the epoch and the `accepted_at` values, but CORE-EPOCH-001 requires a random epoch and CORE-SRV-031 the real clock. An exact replay needs a seam. | `ServerState(epoch=..., clock=...)` take them as construction arguments; neither the command line nor the environment can set them. The replay uses them; production start never does. | `tests/protocol/test_appendix_a.py`. |
